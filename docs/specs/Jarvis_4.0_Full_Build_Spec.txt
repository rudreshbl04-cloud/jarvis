One full upgrade of the same Jarvis project

READ THIS FIRST
For research and an enhanced final build prompt, give this file together with

Jarvis 3.0 is already published. Upgrade the same project and repo. This is
ONE full plan, not V1/V2 apps. The numbered stages are build and test steps.
Nothing requested here is saved for a later version. This is a spec, not a

Rudresh wants the whole app to be clearly better than 3.0, with no bugs or
errors. Treat that as a quality goal, not a promise that software can never
fail. Spend more time testing each stage. Fix failures before moving on.
Do not make Rudresh find the same bug through repeated repair rounds.
Fill small gaps with good judgment. Do not guess about deletion, private
data, paid tools, account access or other risky choices.

1. SCOPE, BACKUP AND BASELINE

Goal: one friendly Jarvis that talks, listens, sees and does real laptop
work, with a new desktop and phone design, local Ollama and optional Gemini.

Keep: Chat, saved history, Notes, Memory, Reminders and Activity log. Keep
Settings, model choice and health checks needed to use them.
Remove: Lecturer mode, its controls and background triggers. Preserve old
notes made by Lecturer. Remove dead links and proven dead code. Show an
inventory before removing any other working feature; "unused" is not a
reason to guess. Keep all installed local models.

Rules:
- Work in the existing project directory. Check the
  real path first. Preserve jarvis.py as a working entry point.
- Do not change Rudresh Studio or the separate rudresh-model project.
- Main Jarvis service stays on port 5000.
- Back up code and data first. Keep old chats, notes, reminders and settings.
- Core mode uses free local tools. No paid server, API key or internet needed
  after setup downloads. Online browsing and Gemini are separate choices.
- No API keys in code, browser files, screenshots, logs, backups or Git.
- Ask Yes/No before risky acts. No means stop. Never bypass that gate.
- Ask before new model or multi-GB downloads. Show source, size, disk need,
  license and purpose. Never download large files during startup.
- Dell has no GPU. Measure real speed; never promise instant vision or
  movie-like voice. Keep the UI and Stop usable while work runs.
- Never say "opened", "sent" or "done" just because a model said it. Check.

Make a feature list for every screen, button, menu and background worker.
For each, record its 3.0 behavior, 4.0 change and test. Every kept part needs
a review; do not add extras while leaving old broken controls untouched.

Tests:
- Inspect actual project files, data paths, startup and installed models.
- Run the unchanged app and save the 3.0 baseline results.
- Restore the backup in a test copy and confirm old data is readable.
- Confirm one project upgrade, not another app or a repo-history replacement.

2. SAFE CODE, DATA AND STARTUP

Use small clear modules if that helps, without breaking the current launch.
Suggested parts: UI, chat, models, voice, vision, PC tools, safety and storage.
Adapt to the code found; do not rewrite blindly just to match this layout.

Use one action queue, one active agent task and one microphone owner. Give
requests IDs. Stop duplicate workers and duplicate writes after retries.
Anchor data paths to the project/data folder, not the current shell folder.
Back up before changing data formats. Use safe writes and clear save errors.
Never hide a load error by quietly starting with empty history.

Keep the shortcut and chosen auto-start flow. Start once. If another app
owns port 5000, explain; never kill an unknown process. Add a health check
with running build, uptime, data access, Ollama and voice state. Keep debug
traces, secrets and full private paths away from network clients.

Tests:
- Start by shortcut and terminal; confirm the same build on port 5000.
- Launch twice; only one service should run.
- Restart and check chats, notes, models and reminders.
- Simulate a failed save and keep the last good data.
- Check the running build matches the files just edited.

3. FULL DESKTOP THEME AND CHAT UI

The current UI is too congested. Redesign it fully: clean, professional,
user-friendly and uncluttered, with clear space and a strong text hierarchy.
Keep only common actions in view; put rare settings in one tidy panel.
Do not cram every mode, status and option into the chat area.
Give Jarvis one calm ARC/RUBI look. Include dark, light and system themes,
clear text, soft accents and reduced motion. Avoid CPU-heavy moving effects.

Layout:
- Sidebar: New chat, saved history, Notes, Memory, Reminders, Activity.
- Top: model choice, local/online state and service state.
- Chat: safe Markdown, lists, links, tables, code blocks with Copy and image
  previews. Escape scripts and unsafe HTML from model output.
- Composer: text, Send, Stop, mic and supported attachment controls.
- Voice panel: input state, transcript, voice, device and mute.
- Settings: model setup, devices, phone link, permissions and diagnostics.

Support chat rename/delete/search, copy reply, regenerate and cancel. Cancel
must stop work, not just hide a spinner. Confirm bulk deletion. Show short
states like Listening, Working and Checking result, not private reasoning.
Remove Lecturer UI and automatic meeting/lecture popups. Preserve old notes.
Do not put technical model labels into every chat reply.

Tests:
- Inspect actual desktop screenshots in both themes at 100% and 125% scale.
- Test every visible button, menu, route, empty state and error state.
- Test keyboard focus, contrast, long code, long names and streaming/Stop.
- Verify Lecturer triggers are gone and old notes remain.
- Put unsafe HTML in a test answer; it must not run.

4. PHONE THEME, PHONE INSTALL AND CONNECTION

Earlier mobile requests: "Our laptop is a main server. The phone is a user
face." Rudresh wants a phone layout like modern AI chat apps, not a shrunken
desktop page. He also asked to download/install it and use it away from Wi-Fi.

Build the phone view in the same app, with the same data and model access:
- Small top bar, slide-out sidebar, full-width chat and readable text.
- Tap targets at least 44 px; no tiny menus or page-wide sideways scroll.
- Composer works with the keyboard open, screen cutouts and bottom controls.
- Themes, history, Notes, Memory, Reminders and Activity work by touch.
- Show Connected, Reconnecting and Laptop unavailable states.
- Let the user pick phone mic or laptop mic. Avoid two devices listening.
- Label phone camera versus laptop camera.

Include both a home-screen web app and a thin Android wrapper project with
a test APK build, for the earlier phone-install request. The wrapper is a
client, not a separate AI app. Check phone OS before Android-only steps. An
iPhone uses the web app, not an APK. Never call a shortcut an APK. Keep APK
signing secrets out of Git. Explain OS installation warnings honestly.

Connection:
- Same Wi-Fi or laptop hotspot can work without internet after local assets
  are installed. Laptop must stay on, awake and running Jarvis.
- Phone installation does not make laptop AI work when the laptop is off.
- Show the current network address; never hard-code an old IP.
- Use secure HTTPS and a tested certificate-trust setup for phone mic and
  camera. Never ask users to disable browser security.
- Core service stays on 5000. If a local HTTPS front end needs another port,
  document it and the route back to 5000.
- Network mode is opt-in. Use private pairing, safe secret storage, hashed
  passwords, attempt limits, session expiry/revoke, route access checks and
  protection against forged requests. No shared default PIN.
- Restrict firewall access to the needed private network. No public port
  forwarding, open tunnel or unauthenticated remote-control endpoints.
- Include an opt-in private connection for away-from-home use, such as a
  suitable private VPN. Verify its current free plan before choosing it.
  It needs internet at both ends and the laptop awake. Ask before adding a
  third-party service or exposing any data. Local-only remains the default.
- Browser pages can be suspended. Do not promise locked-phone, killed-app
  or all-day phone background listening. Test and state device limits.

Tests:
- Inspect 320, 390 and 430 px layouts in portrait and landscape.
- On the actual phone, chat with keyboard open, use Copy/Stop/mic, open
  history, make a note and edit a reminder. Check laptop sync.
- Disconnect internet but keep Wi-Fi: local chat and PC commands still work.
- Turn laptop off: show unavailable, not a fake answer.
- Test HTTPS mic permission allowed, denied and revoked.
- Test home-screen launch, APK launch, wrong pairing and session revoke.
- If remote access is enabled, test on mobile data, not the home Wi-Fi.

5. LOCAL MODELS, GEMINI AND BETTER ANSWERS

Read Ollama's actual model list. Keep all installed models, including
Rudresh's own if present. Check text, image and tool-use abilities instead
of assuming every model supports them. Offer Auto and manual model choice.

Local mode:
- Use the local Ollama API, not cloud routes.
- Choose a measured small model for Fast mode. Warn before large slow models.
- Start with one loaded model on this CPU. Run TEAM in sequence unless RAM
  tests prove safe. Do not use TEAM for every simple question.
- Tune context/reply size to real RAM; do not force huge context windows.
- Improve prompts, examples, relevant note retrieval and tool use. A prompt
  or Modelfile change is customization, not new training or new base weights.
- Save tuning with rollback. Do not edit the separate model project.

Better answers:
- Use plain English and the depth requested. Separate fact from guess.
- Use clock for dates, calculator for maths and real results for actions.
- Retrieve only relevant memory, not the full history on every turn.
- Keep older chat summaries linked to the stored originals where practical.
- Do not invent current facts offline. Cite web pages actually read online.
- Clarify unclear risky targets; do not act on a plausible guess.

Gemini:
- Optional online mode. Key entered in Settings, held only on the server in
  OS-protected storage, masked and never returned to browser code.
- Validate key and currently available model IDs; no guessed hard-coded ID.
- Show free-tier limits and data-use terms. Never turn on billing or paid
  fallback. If free access is unavailable, explain and use local.
- No silent cloud upload of chats, files, camera or screen. Get consent for
  the selected content and route. Do not attach private history by default.
- Handle invalid key, quota, network loss and service errors separately.
- Offer local fallback without losing the message or looping requests.

Tests:
- Compare a fixed 3.0/4.0 set of maths, code, chat, memory and fact questions.
  Save actual outputs and time, not an unsupported quality score.
- Pick every installed model; check real answer or clear capability error.
- Test no internet, missing Ollama/model, low RAM, timeout and cancellation.
- Test Gemini with missing key, bad key, quota error and network failure.
- Verify local-only mode makes no cloud model request.

6. ONE SAFETY GATE AND ONE ACTION ENGINE

All paths use the same checks: text, voice, phone, model tools, screen and
browser control. Flow: request -> exact target -> small plan -> risk check
-> approval if needed -> one action -> verify result -> log -> next step.

Clear low-risk requests can open an app, search a public page, play a local
track, read a selected file or change volume. Do not scan unrelated private
folders just to guess what the user meant.

Ask Yes/No before deleting/overwriting/moving user data; closing unsaved
work; force quit; restart/shutdown; install/uninstall; admin/system changes;
send/post/upload/share; account or permission changes; payment or booking.
Show the exact target, content/changes, recipient/site and cost if any.
Bind approval to a task ID; expire it after a displayed timeout or a target
change. No, timeout or changed target means stop. A past Yes is not a new
approval. A model, webpage or video saying Yes cannot approve anything.
For sensitive voice approvals, require an active confirmation turn and a
specific phrase tied to the card, or a visible click, not ambient speech.

Use allowlisted tools with validated fields, not raw model-written shell
commands. Constrain paths and URLs. Block path traversal, arbitrary code
execution and secret retrieval. Treat documents, pages and screen text as
data, never new instructions to change goals or reveal private information.

Keep Stop visible, plus tray Stop and a global emergency hotkey checked for
conflicts. A stopped task must not restart after reboot. Pause when the
user takes over the mouse/keyboard. Never fight the user for control.

Tests:
- Test No, expired approval, changed target and duplicate/retried requests.
- Test a document/page asking to delete files or reveal keys: no tool runs.
- Test bad tool fields and a path outside the permitted folder.
- Stop mid-task; no further actions may run or return after restart.

7. VOICE INPUT AND WAKE WORD

Primary desktop voice must run locally, not rely on an online browser speech
service. Choose a free CPU-ready speech-to-text engine. Benchmark a small
existing model or ask before downloading one.

Start with the existing "Hey Rubi" wake phrase. Let the user change/test it.
Check the wake engine's custom-phrase support, license and key needs before
choosing it. A tested local phrase-detection method is acceptable; do not
claim a library supports a custom phrase without checking.

Visible states: Off -> Waiting for wake word -> Listening -> Working ->
Speaking -> Listening. Also show Waiting for approval and Error.

Rules:
- Mic off after installation until the user enables hands-free.
- Wake phrase never becomes the chat question.
- "Hey Rubi" alone wakes and acknowledges; combined phrase/command runs once.
- Show recognized text and allow correction.
- Keep at least a 10-second listening window after wake, with pause detection
  and an adjustable timeout, not endless recording of every conversation.
- One mic owner. Pause/filter speaker echo to stop Jarvis waking itself.
- Turning mic off in UI stops capture on the backend too.
- Device failure gives a clear safe state, not endless retries.

Real-mic tests:
- Wake phrase alone ten times; phrase plus command ten times. Record results.
- Background speech/music for 15 minutes; record false wakes and CPU use.
- Quiet speech, fan noise, Indian English, pauses and a changed input device.
- Denied access, unplugged mic and recovery. No wake text sent as a question.

8. HANDS-FREE TALK AND BETTER VOICE OUTPUT

Aim for warm, friend-like talk with short spoken answers. Tony Stark is a
style reference, not a promise of human intelligence or instant performance.
Use a free local voice as the offline base. Offer previews, rate, volume,
output device and pitch where supported. Prefer clear Indian English if a
suitable free local voice exists. Online neural voices are opt-in and must
be labeled online, not passed off as offline.

Speak in short chunks. Summarize long answers; do not read code punctuation
and tables unless asked. Stop speech immediately when Stop is pressed.
Support "stop talking" without waiting for a language model.

After a reply, listen for the next turn within the chosen window, then return
to wake standby. Support interruption if audio hardware permits it. If echo
prevents safe full-duplex talk, offer clear half-duplex mode. Show whether
the tray process is listening when the browser window is closed. Provide
pause, resume and quit. Handle sleep, device loss and phone limits honestly.

Tests:
- A 20-turn talk/command session without touching Send.
- Five minutes of silence with no invented prompts or actions.
- Interrupt a long reply; measure Stop delay and confirm next command works.
- No internet: wake, speech input and base voice still work.
- Close/reopen UI, pause from tray, sleep/wake laptop. Display and actual
  mic state must match. No old queued command may run on wake.

9. MUSIC, APPS, FOLDERS AND FILES

Use structured tools to:
- Find/open installed apps using real launch targets, not web substitutes.
- Close apps with unsaved-work checks; never force kill by default.
- Open a folder, then find/open a file inside it by name/type.
- Ask on multiple matches. Show chosen path in the result.
- Play/pause/next/previous/mute/set volume for a known player.
- Find tracks in a selected local music folder by title/artist.
- Open a named site or web search when internet is present.

Web music needs internet and legal site access. Do not promise every player
supports the same controls. Ask which player if several are active. Handle
spaces, Unicode names, missing files/apps and no default file handler.

Tests:
- Open Notepad, Downloads and the installed WhatsApp app if present; verify
  actual windows, not just a reply claiming success.
- Open a file in a folder with spaces. Test two matching lab files: ask.
- Play a local track, pause, next and mute; verify player state.
- Test missing app/song, locked file, multiple players and unsaved document.

10. INSTALL AND UNINSTALL

Show exact package, publisher, source, version, size, license/cost and change
before approval. Use verified vendor/package-manager sources, not an advert
or first search hit. Check signatures where available. Warn about app data
loss on uninstall. Each install and uninstall needs its own Yes/No.

Respect UAC/admin prompts. Ask the user to handle a prompt that cannot be
safely controlled. Never bypass UAC, disable antivirus or weaken security.
Check installed package state and launch after completion. Starting an
installer is not proof of success. Do not silently retry an unclear outcome.

Tests:
- No must make no change.
- With approval, install/launch/uninstall a safe test app. Separate approvals.
- Test failed download, denied UAC, already installed and pending restart.
- Verify no unrelated app or user data changed.

11. CAMERA VISION THAT USES A REAL IMAGE

Preview alone is not vision. Capture a fresh frame from the selected camera
and pass the actual image to a tested image-capable local model. Reuse
installed vision models that pass the test. Text-only models cannot see.

Provide camera selector, preview, capture time, Analyze, Cancel and Off.
Start with small on-demand frames for this CPU; preserve enough detail.
Default to snapshots, not full-resolution live AI video. A local preview
can run without analyzing every frame. Any continuous-analysis mode must
show its measured delay and have a clear stop control.

Describe only visible facts, state uncertainty and request a better view
when needed. Do not invent identities or hidden facts. No dependable medical,
safety or face-ID claims. Keep raw frames temporary by default. Off releases
the camera/worker. Cloud image use needs clear consent.

Tests:
- Show three ordinary objects, swap one and ask again. Fresh image required.
- Ask about an object outside the view; Jarvis must admit it cannot see it.
- Test dark room, covered lens, camera busy/missing and denied permission.
- Verify actual image input reaches the model and stays local in local mode.
- Measure cold/warm response time and show expected delay.

12. FULL SCREEN VISION

Capture the real laptop screen through a local desktop helper. Browser screen
sharing is a separate user-permission path, not silent access to all windows.
Support full display, chosen display and chosen area. Handle multiple
monitors, negative coordinates and Windows scaling. Show preview/timestamp.

Use local OCR for small text, plus image analysis for layout. Use crops when
resizing makes text unreadable. Capture again after a change. A blank or
protected window must produce a clear limitation, not a made-up description.

Screen watching is opt-in. Prefer capture on request/action boundaries, not
constant full-resolution inference. Show state/Stop. Do not retain screens
by default or silently upload passwords/private screens to Gemini.

Tests:
- Read a unique test sentence in Notepad; change it and read the new text.
- Full screen, crop, 125%/150% scaling, and two monitors if available.
- Minimized/protected windows, denied access and blank capture.
- Stop screen access; no further capture. Confirm no stale image reuse.

13. REAL AGENTIC BROWSER, APP AND CURSOR WORK

Use Stage 6 for every step. Prefer direct APIs, accessibility controls and
browser elements. Use cursor pixels only with a fresh view and checked
coordinates. Never let model text execute directly as commands.

Loop: plan -> observe -> act -> check -> next step. Show a short plan and
step log. Start with a small cap, such as 12 actions, plus a visible time
limit. Pause/ask at the cap, not endless self-repair. Simple commands should
use direct routing rather than a slow model plan.

Browser:
- Open/search, follow links, read, scroll, change tabs and fill harmless
  draft fields when asked. Check real URL, title and result.
- Use a dedicated local browser profile or explicit approved connection.
  Do not copy private cookies or weaken browser security.
- Pause for login, CAPTCHA, verification and important account choices.
- Before send/upload/account change/payment, show the exact final action
  and get its approval. Drafting does not authorize submission.
- Public browsing needs internet. Local pages can still work offline.

Apps/cursor:
- Click/double-click/right-click, scroll, type, select, drag and keys.
- Verify foreground app, title and target before typing/clicking.
- Map coordinates for monitor origin and DPI scale from a fresh capture.
- Pause on user mouse/keyboard input. Never type into a newly focused app.
- Re-observe before limited retries. Never repeat send/delete/pay clicks
  when the first result is unclear.
- UAC/secure desktop or unsupported controls require a manual step.

"Full laptop control" means broad supported tools, not unlimited permission
or perfect control of every app. Small models may fail at long plans. Ask
when needed rather than invent success or a dangerous workaround.

Tests with dummy data in a safe test folder:
- Open Notepad, type and save an agreed test file; verify file contents.
- Find/open a named file inside a folder.
- Search a public topic and summarize a read page with its actual URL.
- Test changed page, no network, user mouse takeover and changed focus.
- Reject a risky action and use emergency Stop mid-task.
- Verify no wrong-app typing, stale clicks or task resuming after Stop.

14. NOTES, MEMORY, REMINDERS AND ACTIVITY

Notes: create, view, search, edit, rename and safely delete.
Memory: show saved facts, let the user correct/delete them and distinguish a
passing chat mention from a request to remember. Keep memory local.
Reminders: create, list, edit, delete, snooze and done. Store timezone and
intended time. Clarify vague dates/times before scheduling.

Reminders survive restart. If the laptop slept through the due time, show a
missed reminder on wake; never claim an alert fired while powered off. Avoid
duplicate alerts after crashes.

Activity: timestamp, task ID, tool, target summary, approval state, result
and short error. No passwords, keys, raw audio or full screens by default.
Include retention, clear and export controls; confirm risky clearing. Exports
must not silently include secrets or private captures.

Tests:
- Create/find/edit/delete a note and memory fact; restart and verify storage.
- Make a reminder due in two minutes. Test snooze/done/delete and restart
  before due time. Test sleep across due time and one alert only.
- Check logs for secret leakage, clear errors and correct action results.

15. SPEED, STABILITY, TESTING AND RELEASE

Record real Dell measurements: startup, UI response, wake detection,
speech recognition, speech start/stop, cold/warm model first-token time,
answer rate, camera/screen latency, peak RAM and idle CPU use.

Use these measurements to choose smaller images, model load and context.
Do not fake speed with stale answers. Keep Stop and UI responsive during
inference. Bound queues; release unused devices/models; no busy idle loop.

MANDATORY GATE FOR EVERY STAGE
- Build a checklist for every button, option, command and background feature
  changed or affected. Test happy path, bad input, empty state and failure.
- Run automated tests and actual use checks. Label mocks as mocks.
- Save evidence: action result, logs, output files or real UI screenshots.
- Mark each check Pass, Fail, Blocked or Not tested. Not tested is not Pass.
- Fix failures at their root, add a regression test and repeat that stage's
  checks plus earlier checks affected by the fix. Do not move on with known
  failures just to report progress. Take the extra time needed now.
- If hardware, access or a user decision blocks a check, state it clearly.
  Never invent a pass. Do not claim the whole upgrade finished while blocked.

Final gates:
1. All stage tests pass; old 3.0 regression checks still pass. No data loss.
2. Every kept option has a documented 4.0 improvement or a verified reason
   to preserve its already-good behavior. No ignored broken legacy controls.
3. Real tests cover voice, camera, screen, actions and phone, not just APIs.
4. Internet-off tests pass for core local features with local assets present.
5. Gemini is tested separately with a user-supplied key and consent.
6. A 30-minute mixed chat/voice/action session has no crash, duplicate task,
   growing queue, stuck mic or unexplained resource growth.
7. Reboot, sleep/wake, network loss and device/model failure recover safely.
8. Actual screenshots in both themes are inspected on desktop and phone.
9. Rudresh runs the demo below. His real failure overrides a generated
   "all pass" report. No unsupported promise of zero possible future bugs.

Acceptance demo:
- Launch from the normal icon. Enable hands-free and say "Hey Rubi".
- Ask a question, open an installed app, play a local track and open a file.
- Give a second command without touching Send.
- Ask about camera objects, change one and ask again.
- Read new screen text, then change it and check again.
- Run one safe multi-step browser/app task; use Stop in the middle.
- Reject uninstall and verify nothing changed.
- On the phone, chat with keyboard open, use HTTPS mic and create a note.
  Check that note on the laptop.
- Disconnect internet and repeat local chat and a local command.

Deliver in this same upgrade:
- Working code, tested dependency list, launch scripts and diagnostics.
- README for setup, local use, Gemini, phone HTTPS, APK build/install,
  optional private remote use, hardware limits and all safety controls.
- Model/asset size list and license notes for code, voices and models.
- Migration notes, backup/restore steps, test report and real evidence.
- Clean Git changes: no keys, pairing secrets, chats, private screenshots,
  model weights, virtual environment, giant backups or signing secrets.
- Reviewed change list for the same repo. Ask before push/publication.

Never call a button, stub or reply a working feature. If a requested target
cannot work on this hardware/OS, name the limit and tested alternative.
Get Rudresh's decision before cutting agreed scope. The goal is a finished,
clearly better 4.0, not another cycle of him discovering obvious errors.
